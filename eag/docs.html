Documentation

Everything you need to connect a backend, expose it as governed natural-language tools, and put your AI agents in front of it — safely.

Core concepts

Five ideas run through the whole product:

  • System — a connected backend (ServiceNow, Workday, SAP, a Dataverse table, or anything that speaks MCP). One image fronts many systems; you turn them on and off.
  • Tool — a canonical, plain-language capability an agent calls by intent (e.g. case.create, hr.timeoff.balance.get). The catalog is stable; the backend behind a tool can change without the agent noticing.
  • Scope — a permission string (e.g. hr.read, case.write) a tool requires. A caller only sees tools their scopes grant.
  • Mapping — how a tool actually runs on a live backend: which table answers it, whose rows, and how columns become fields. Mock systems serve samples with no mapping; a live system needs one.
  • Tier & gating — every tool is read, write, or privileged. Policy gates decide confirm-before-write and block/approve for privileged actions.
The golden rule: agents bind to the canonical catalog, never to a backend. That's what lets you swap or migrate backends in seconds without touching a single agent.

The console

Everything below is done from the admin console (served at /admin), no YAML editing required. Eight tabs:

  • Systems — the fleet: toggle systems on/off, expand a row for tools, gating, config, and Connect.
  • Tool catalog — the canonical contract; add custom tools here.
  • Mappings — bind a tool to a live table.
  • Identity probe — "what would this user see?" before they ask.
  • Live audit — every call, streaming, with identity + outcome.
  • Users — console roles and tool-scope grants.
  • Onboard a system — generate a new system's manifest.
  • Licensing — install a key, see seats and the expiry countdown.

Use the ☀/◐ button in the header to switch light/dark.

Add a system (connect a backend)

Onboard a system→ Systems→ Connect…→ toggle on
  1. Open Onboard a system. Give it an id (e.g. acme-crm), pick the adapter (the driver for that vendor — ServiceNow, Salesforce, Workday, SAP, Snowflake, Dataverse, mcp-proxy to federate an existing MCP server, or mock), a display name, and (optionally) a base URL. Generate the manifest — it always starts disabled and references secrets by env-var name only.
  2. On the Systems tab the new system appears under its domain group. Click Connect… to open the credential dialog: choose an auth method, enter the connection parameters, Test, then Save & connect. Secrets go to a gitignored store — never into config or the image.
  3. Flip the toggle switch on. Its tools appear to authorized agents on the next tools/list.
No API yet? Model the target in Dataverse, serve it live through the same catalog to prove the agent experience, then repoint to the real backend later — all agent traffic switches in seconds. (The Dataverse staging capability is a Team-tier feature.)

Create a tool & its scope

Tool catalog→ Add a custom tool

Custom tools extend the catalog without touching code. In Tool catalog → Add a custom tool, set:

  • id — dotted, e.g. crm.lead.get.
  • tier — read / write / privileged (drives gating).
  • classification — internal / public / pii.
  • scopes — the permission(s) a caller needs, e.g. crm.read. Define the scope here — a tool and its scope must exist before you can map it to a system.
  • description — write it for the model; it drives routing.
  • input schema — optional JSON Schema for the tool's arguments.

A custom tool overrides nothing in the base catalog; it's additive. Grant the scope to users on the Users tab.

Map a tool to live data

Mappings→ pick system + tool→ table + scope + columns

A tool's catalog entry says what it is; the mapping says what it does on a real backend. In Mappings:

  1. Pick the system and the tool.
  2. Which table answers it? — choose the binding mode (one record / a list / create / aggregate / hand-off) and the entity set.
  3. Whose rows? — scope to the caller (by column), the caller's own identity row, or explicitly org-wide.
  4. Draw the lines — map each output field to a table column (dropdowns are fed by live table metadata). Optionally filter by tool input, set an order/limit, and decode picklists.
  5. Save mapping — validated server-side, applied on the next call.
Prerequisite: the tool (and its scope) must already exist in the Tool catalog before it can be mapped. Custom tool first, mapping second.

Govern by tier

Open a system's row and set its gating: write = require-policy / require-approval / off; privileged = block / require-approval / off. Loosening gating prompts for an audited reason — security sign-off is an event, not a checkbox.

Before you hand tools to agents, use Identity probe: type any scope set (or pick a persona) and see the exact tools that identity would be served — allowed, gated, or hidden — with the reason. Governance you can demonstrate, not assert. Everything runs through Live audit: user, tool, system, outcome, latency.

Users & roles

Your identity provider (Entra) proves who a caller is; the Users tab decides what they may do: a console role (admin / read-only) and granted tool scopes. Add a user by email or Entra object id, pick a role, list their scopes, and save. Unlisted users fall back to the configured default (usually: nothing until granted).

Licensing

Every install starts with a 30-day trial — all features unlocked. A signed key then sets your tier, verified offline (air-gap friendly, no phone-home). In the Licensing tab (or click the plan badge in the header): paste the key, Verify & install. It hot-applies and persists.

The header badge and Licensing tab show a days-remaining countdown (amber at 14 days, red at 5). Renew and install the new key before it lapses, or the gateway locks and tool calls refuse until a valid key is installed. Mock and demo systems are always free, so evaluation is never blocked.

Deploy

EAG ships as one container image, config per customer. Run it on Docker, Azure Container Apps, App Service, on-prem, or fully air-gapped. Point it at your Entra tenant, mount a writable data volume, and connect your systems from the console. Your systems never leave your cloud.

docker run -d -p 3000:3000 --env-file .env \
  -v eag-data:/app/data  your-registry/eag-gateway:latest

Console at /admin, MCP endpoint at /mcp. Register that one endpoint in Copilot Studio, Azure AI Foundry, Claude, or any MCP client, and it fronts your whole governed fleet.
